# Deployment preparation and release gates

This repository review prepares a release; it does not provision, purchase, deploy or point DNS at any service. Do not interpret a version label as production acceptance.

## Hosting decision

Recommended initial topology: one Linux VPS, an HTTPS reverse proxy serving the built web application, a single long-lived NestJS process, a loopback Python worker, durable AI files and privately reachable PostgreSQL/MongoDB. Keep one active MQTT/controller instance. Size CPU/RAM using real image inference and database load; do not promise a small free instance will fit Torch plus both databases.

Vercel can host the static React build. Use repository root as build root, `npm ci && npm run build:web`, and `apps/web/dist` as output. Set public `VITE_API_BASE_URL=https://<api-domain>/api` before building; configure an SPA fallback for `/trace/*` and authenticated routes. Add the exact HTTPS frontend origin to API CORS and use the final web origin for `TRACE_PUBLIC_BASE_URL`. No backend/worker/provider secrets belong in Vercel frontend variables.

Render is an alternative for paid, continuously available services with persistent storage, but the current Python integration deliberately permits loopback only. Splitting API and worker into separate Render services requires a reviewed private-network integration change rather than simply replacing the URL. Free Render services sleep after 15 minutes without inbound traffic and cannot attach persistent disks, making that tier unsuitable for the current always-on MQTT/controller and local AI storage architecture. See [Render free services](https://render.com/docs/free) and [persistent disks](https://render.com/docs/disks). Vercel Functions have finite execution duration; a long-lived controller should not be implemented as a request-scoped function. See [Vercel function limits](https://vercel.com/docs/functions/limitations). Service plans and limits must be rechecked when provisioning.

## Production authentication and retained local demo

`NODE_ENV=production` requires `AUTH_MODE=database`, persistent storage, explicit HTTPS CORS/trace origins and a dedicated JWT secret. Database mode uses existing accounts, ignores `AUTH_TEST_*` notes, creates no test accounts, rejects mock SMS and disables Swagger. An unconfigured SMS provider fails closed without a fake OTP. Real Twilio/SpeedSMS require their explicit recipient settings; SMTP verification remains unavailable until configured. Database mode can explicitly bind `API_HOST=0.0.0.0` for a container; default is loopback behind the VPS proxy. Mock Auth is always loopback-only and remains forbidden in production.

The owner's local `.env`, acceptance accounts, Twilio numbers, Gmail and provider credentials are retained unchanged for the thesis demo. Use a **separate** server file, starting from `deploy/api.env.example`; do not replace the local demo environment. A restored database keeps existing accounts/password hashes; it does not require public Admin registration or re-seeding. Changing the production JWT secret/issuer requires fresh login and does not delete accounts. Real public launch should use dedicated secrets and review demo-account access; do not delete the local fallback.

SMTP and Trial Twilio are currently explicitly scoped to demo recipients. Decide the real deployment's supported recipient policy, provider account limits and cost controls before public registration/password recovery. Do not silently open the allowlist.

The tested firmware has no MQTT username/password configured. Its station ID is not secret. A public/shared broker allows untrusted publishers to imitate telemetry or ACK; TLS alone does not authenticate the sender. Choose an isolated broker/network and a compatible access-control approach with the hardware owner before treating remote actuation as publicly production-ready. Keep the tested topic/payload contract unchanged unless a separate firmware change is approved.

## Release gates

1. Select hosting, operating system, domain and backup destination; no subscriptions are created by repository scripts.
2. Verify production database authentication and all mock-route protections on the target host. Use dedicated server JWT/internal secrets and review demo passwords before public launch while retaining the untouched local demo configuration. Do not publish private local account notes or database contents.
3. Provision databases with real authentication and private access. MongoDB must be a replica set for transactional cultivation/task/AI behavior. The local Compose file is for a trusted development machine; its unauthenticated MongoDB must never be exposed as a production database.
4. Copy model, original/prepared PDFs and persisted AI storage securely. Install platform-compatible Python dependencies and verify the actual weights on the target OS; the Windows inference lock alone is not Linux evidence.
5. Back up existing data and verify restore. Use a maintenance window for final data transfer. Apply only pending migrations explicitly; do not re-seed or generate fake operational records on production startup.
6. Build web/API from a clean checkout using `npm ci`; run isolated tests and dependency/security review. Keep provider secrets server-side and outside build artifacts. Verify no local archives, credentials, PDFs or weights are present in Git's release tree.
7. Configure HTTPS, exact CORS origin, trace origin, request/body/time limits, upload directories and restrictive filesystem ownership. Expose only HTTP(S); firewall database/worker/API ports from the public network. Proxy `/api/*` unchanged, preserving Authorization and disabling caching of private responses. Forward deep links to web `index.html`, but return actual API errors for `/api/*` rather than the SPA page.
8. Start only one API/controller with graceful shutdown/restart. Keep Python private on 127.0.0.1:8001. Probe `/api/health` and `/api/health/ready`; database readiness alone does not attest to model/MQTT/provider health. Disable public Swagger or protect it at the reverse proxy.
9. Complete four-role, real provider and hardware checks in [RUNBOOK.md](RUNBOOK.md), including negative authorization, missing ACK and reboot. Document observed physical results separately from receipt logs.
10. Test off-host restore, retained file permissions, failure/recovery, monitoring, log redaction and rollback before changing DNS. Rollback code against a compatible schema; never undo released migration checksums or delete volumes.

## Rollout checklist

Record release commit, configuration version (without secrets), migration ledger, model hash, corpus hashes, backup hash and actual manual test results. Begin with a restricted pilot and monitored hardware. Keep fabricated initialization identifiable internally; do not present synthetic measurements as collected production evidence. Account deletion/data-retention policy and AI accuracy/out-of-domain evaluation remain separate operating concerns.

No deployment was performed during this preparation. The local setup can continue to run while the blocking production decisions are resolved.

## First VPS deployment: practical sequence

These steps are for a later, explicitly approved rollout. No VPS or domain has been purchased. Keep local demo operation available throughout.

1. **Select a provider and budget.** Choose a supported Ubuntu LTS VPS near intended users. A starting capacity estimate for this single-host CPU inference topology is 4 virtual CPUs and 8 GB RAM; actual image inference plus database memory must be measured before buying a plan. Persistent disk, snapshots and off-host backups matter more than a free trial. Confirm SMTP and outbound broker ports are permitted by the provider. Do not buy an expensive annual plan before the target-host smoke test.
2. **Prepare access.** Use SSH keys, a non-root operator, security updates and a firewall. Expose SSH to your management addresses and HTTP/HTTPS publicly; keep database, API and Python ports private. Record recovery access. Install a Node version satisfying the workspace engines, Python/venv, Docker Compose if using containers, and Caddy from their official instructions. Check actual executable paths before installing the supplied systemd units; `/usr/bin/node` is a template path, not a promise about every installation.
3. **Prepare the databases.** Either use managed PostgreSQL/MongoDB with authenticated private/TLS access or configure them securely on the VPS. MongoDB must support replica-set transactions. Do not copy the unauthenticated local MongoDB service onto a public interface. Save credentials in server environment files, not Git. Prove both connections with a health check before copying business data.
4. **Install a reviewed release.** Clone this repository into `/srv/smart-durian`, check out the exact release commit, run `npm ci --include=dev`, `npm run build` and `npm run build:web`. Build tools are needed even when the eventual server runs in production. A clean checkout excludes the weights and PDFs intentionally. Create the service account and private writable directories `ai/storage/diagnostics`, `ai/storage/rag-documents` and `ai/.runtime`; make only those directories writable to the service. Code/model files should be read-only to the running services.
5. **Transfer data and AI assets.** Pause local writers for the final backup, verify it, transfer the JSON plus `.json.assets`, and restore into a new target database. Review the generated target names before selecting the server connection strings. Transfer `best.pt` and original/prepared PDFs separately and verify hashes. Do not invoke development seed on the restored production database. Install platform-compatible inference requirements in the server venv and run a real model smoke test.
6. **Configure services without exposing them.** Copy the two `deploy/*.env.example` files to `/etc/smart-durian/api.env` and `ai.env`, fill values privately and restrict permissions. Share `AI_INTERNAL_TOKEN` between these two files; the worker needs no DB/Twilio/Groq keys. Configure SMTP/Twilio and enable AI/MQTT only when each dependency is ready. Adjust the supplied systemd unit paths and user, validate them with `systemd-analyze verify`, then start exactly one API and one loopback worker. Check local health, login, files and restart retention. API environment comes from systemd, not the developer's `.env`.
7. **Connect the domain and HTTPS.** After choosing a domain, create DNS A records pointing at the VPS IPv4 address. Add AAAA only if IPv6 routing/firewall is actually configured. Replace `farm.example.com` in `deploy/Caddyfile`, CORS and trace origin with that domain. Validate with `caddy validate --config <path>` before enabling it. Caddy can obtain HTTPS certificates after DNS and ports 80/443 are reachable. Keep `/api` proxied without stripping the prefix. Check `/trace/<code>` on a phone, including a direct deep link and QR scan.
8. **Run acceptance, then announce availability.** Execute the runbook's four-role and physical hardware scenarios over HTTPS, verify provider errors/quotas, test a fresh backup/restore and record the release hash. Review broker isolation before remote actuation. Keep a rollback code revision and untouched local demo setup. Do not start both local and VPS controllers against the same station during a transition.

The provided systemd/Caddy templates are preparation artifacts; their syntax and runtime still need validation on the chosen Linux host. No server binaries or cloud resources were installed by this review. For Vercel, the included `vercel.json` prepares static routing only; the API and private worker still need their own reviewed long-lived host.
